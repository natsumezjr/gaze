# 眼动追踪项目 - 前后端与接口分析

## 一、整体架构概览

本项目**不是**传统的「浏览器前端 + HTTP 后端」架构，而是**单进程、多线程的桌面应用**：

- **“后端”**：识别、拟合、数据管道等核心逻辑，运行在子线程/线程池中。
- **“前端”**：Tkinter 校准 UI（`client/kappa/ui.py`），运行在主线程。
- **通信方式**：进程内**事件/回调**（`CALLBACK_MANAGER`），无 HTTP、无 WebSocket、无 REST API。

```
┌─────────────────────────────────────────────────────────────────┐
│                        主进程                                     │
│  主线程: Tkinter UI (EyeCalibrationApp)  ←→  mainloop()          │
│              ↑ 事件/回调 ↑                                        │
│  子线程: RecognitionManager → 发 RECOGNITION_COMPLETE              │
│  线程池: FittingScheduler / FittingManager                        │
│          ↑ 发 CALIBRATION_* / ROUGH_GAZE_UPDATE                   │
│          ↑ 收 CALIBRATION_POINT_SUBMIT / CALIBRATION_COMPLETE    │
│  数据:   DATA_PIPELINE_MANAGER, FRAME_ID_MANAGER (内存)           │
└─────────────────────────────────────────────────────────────────┘
```

---

## 二、“前端”与“后端”划分

| 角色 | 目录/模块 | 说明 |
|------|-----------|------|
| **前端（UI）** | `project/client/kappa/` | Tkinter 校准界面：显示校准点、接收用户确认、显示粗略注视点 |
| **后端-识别** | `project/core/recognition/` | 摄像头/图像 → 人脸与关键点 → 发 `RECOGNITION_COMPLETE` |
| **后端-拟合/调度** | `project/core/fitting/` + `project/main.py` 中 `FittingScheduler` | 收识别完成 → 拟合 → 发标定请求/粗略视线 |
| **后端-数据** | `project/data/`, `project/managers.py` | 帧数据、frame_id、标定样本存储 |
| **事件总线** | `project/managers.CallbackManager` | 所有“前后端”通信都经此 emit/register |

## 三、接口定义（事件 + 数据结构）

所有“接口”都是**事件名 +  payload 约定**，由 `project/events/event_types.py` 和 `project/data/data_models.py` 定义。

### 3.1 主流程事件（核心逻辑）

| 事件名 | 方向 | 触发方 | 接收方 | Payload | 说明 |
|--------|------|--------|--------|---------|------|
| `RECOGNITION_COMPLETE` | 识别→调度 | RecognitionManager | FittingScheduler | `frame_id: int` | 一帧识别完成，可做拟合 |
| `FITTING_START` | 调度→（广播） | FittingScheduler | （暂无订阅） | `frame_id: int` | 已提交拟合任务 |
| `SYSTEM_STOP` | 主/异常 | main / 键盘中断 | 各模块 | 无 | 请求整机停止 |

### 3.2 标定相关事件（UI ↔ 调度）

| 事件名 | 方向 | 触发方 | 接收方 | Payload | 说明 |
|--------|------|--------|--------|---------|------|
| `CALIBRATION_START_REQUEST` | 调度→UI | FittingScheduler | EyeCalibrationApp | `frame_id: int` | 需要开始/继续标定 |
| `ROUGH_GAZE_UPDATE` | 调度→UI | FittingScheduler | EyeCalibrationApp | `calibration_request: CalibrationRequest` | 当前帧粗略注视点（用于显示蓝点） |
| `CALIBRATION_POINT_SUBMIT` | UI→调度 | EyeCalibrationApp | FittingScheduler | `calibration_response: CalibrationResponse` | 用户确认一个标定点 |
| `CALIBRATION_COMPLETE` | UI→调度 | EyeCalibrationApp | FittingScheduler | `calibration_result: dict` | 27 点标定全部完成 |

### 3.3 数据结构（标定接口契约）

- **CalibrationRequest**（调度 → UI）  
  `frame_id`, `eye_type`（left/right）, `intersection: Point2D`（屏幕交点）

- **CalibrationResponse**（UI → 调度）  
  `frame_id`, `eye_type`, `target_pixel: Point2D`, `background_color: str`

- 其它：`Point2D` / `Point3D`、`RecgFitDataManager` 等见 `project/data/data_models.py`。

## 四、发现的问题与建议

### 4.1 依赖与架构不一致

- **Flask、requests** 在 `pyproject.toml` / `requirements.txt` 中声明，但**代码中未使用**（仅 `landmark_extractor` 里有 mediapipe 的 https URL）。
- **建议**：若不打算做 Web 服务或对外 HTTP 接口，可从依赖中移除 `flask`、`requests`，避免误解为“有 Web 后端”。

### 4.2 关闭窗口时未发系统停止

- 用户点击窗口关闭（X）时，只执行了 `EyeCalibrationApp.close()`（destroy 窗口），**没有**调用 `main.request_system_stop()`，因此 `stop_event` 可能未被设置。
- 表现：mainloop 退出后，主线程会卡在 `while not stop_event.is_set(): ...` 等待 `recognition_future.done()` 或超时，退出不够干净。
- **建议**：在 UI 上绑定 `WM_DELETE_WINDOW`，在关闭时调用 `request_system_stop()`（或通过回调/事件通知 main 调用），保证关闭即停。

### 4.3 事件契约未集中文档化

- 事件名、payload 类型、谁发谁收分散在 `event_types.py`、`main.py`、`ui.py` 中，新人难以一眼看出“接口”全貌。
- **建议**：在 `docs/` 或 `events/` 下维护一份“事件接口表”（如上表），并在 `event_types.py` 或 data_models 里用注释引用；对 `CalibrationRequest` / `CalibrationResponse` 的字段保持单一定义（避免重复 __init__ 与 dataclass 混用）。

### 4.4 线程与 UI 更新

- 回调在**触发线程**中执行；`FittingScheduler` 在线程池线程里 `emit(ROUGH_GAZE_UPDATE, ...)`，UI 侧在 `_on_rough_gaze_update` 里用 `self.root.after(0, ...)` 投递到主线程，做法正确。
- 建议：所有“在 UI 上改控件”的逻辑都经 `root.after(0, ...)` 或等效方式，避免跨线程直接操作 Tk。

### 4.5 单例与生命周期

- `EyeCalibrationApp`、`FittingScheduler`、`CallbackManager`、`FrameIdManager`、`DataPipelineManager` 等均为单例，且 UI 在 main 中通过 `get_instance()` 创建。
- 若将来做“多窗口”或“重入标定”，需注意单例与 `mainloop()` 只运行一次的限制；当前单窗口标定流程是自洽的。

## 五、若将来要加“真”前后端（如 Web）

若以后希望：

- 浏览器/移动端做标定界面，或  
- 多机/多进程协作，

可考虑：

1. **在现有进程内增加一层 HTTP/WebSocket 服务**（例如用 Flask/FastAPI）：  
   - 将现有“事件 + CalibrationRequest/CalibrationResponse”映射为 REST 或 WebSocket 消息；  
   - 服务端仍通过 `CALLBACK_MANAGER.emit/register` 与现有 FittingScheduler/UI 逻辑对接（或先替换为“无 UI 的标定服务”再对接）。

2. **接口设计**：  
   - 标定开始：POST `/calibration/start` 或 WS `calibration_start`（可带 `frame_id`）。  
   - 标定点位提交：POST `/calibration/point` 或 WS `calibration_point`，body 与 `CalibrationResponse` 一致。  
   - 标定完成：POST `/calibration/complete` 或 WS `calibration_complete`。  
   - 粗略视线（若需 Web 端显示）：WS 服务端推送与 `CalibrationRequest` 或当前视线点等价的数据。

3. **当前 Tkinter UI** 可保留为“桌面模式”，与“Web 模式”共用同一套 FittingScheduler 与事件定义，仅把“发/收”从 Tk 回调改为 HTTP/WS 的入站/出站即可。

## 六、小结

| 项目 | 结论 |
|------|------|
| 前后端形态 | 单进程：Tkinter 前端 + 识别/拟合/调度后端，无 HTTP 接口 |
| 接口形式 | 进程内事件（CallbackManager）+ CalibrationRequest/CalibrationResponse 等数据结构 |
| Flask/requests | 已依赖未使用，可删或预留为扩展 |
| 关闭逻辑 | 建议窗口关闭时调用 request_system_stop，保证退出一致 |
| 文档与契约 | 建议集中维护事件与 payload 文档，并统一 Request/Response 定义 |

以上为当前代码库下的前后端与接口分析；若你后续要加具体 API 或改事件名，可以在此基础上再细化一版“接口变更说明”。
