# 前端效果与前后端连接观察

## 一、当前架构是否更简明合理

### 1.1 已改善的方面

| 方面 | 现状 | 说明 |
|-----|------|------|
| **线程分工** | 主线程 = 编排 + Tk；识别 = 独立线程；拟合 = 专用线程池 | 识别不再与拟合抢池子，回调里不再在识别线程做重活，边界清晰。 |
| **前后端边界** | 后端只发事件（`CALIBRATION_START_REQUEST`、`ROUGH_GAZE_UPDATE`、`GAZE_POINT_UPDATE`、`REQUEST_CALIBRATION_UI_CLOSE`、`SYSTEM_STOP`），不直接引用 `EyeCalibrationApp` | FittingScheduler / FittingManager 不依赖具体 UI 实现，便于接 Unity/Web。 |
| **UI 线程纪律** | 所有写 `gaze_points` 与 Tk 控件的逻辑都经 `root.after(0, ...)` 在主线程执行 | `add_gaze_point` 仅调度，`_add_and_draw_gaze_point` 在主线程里 append + 绘制，无跨线程写共享状态。 |
| **前端抽象** | `FrontendAdapter` 四方法：`show_calibration_start`、`update_rough_gaze`、`show_gaze_point`、`request_close` | Tk 实现该接口；后续 Unity/Web 可实现同一接口并注册同一批事件，协议统一。 |
| **关闭流程** | 标定完成 / 系统停止时通过事件 `REQUEST_CALIBRATION_UI_CLOSE` / `SYSTEM_STOP` 通知前端，前端在回调里 `request_close()` | 后端不再直接调 `ui.close()`，由前端适配器自行关闭。 |

整体上，**连接方式更简明**：单向「后端发事件 → 前端适配器收事件并更新 UI」，加上「前端发事件 → 后端收事件」（标定点提交、标定完成），契约清晰，便于扩展。

## 二、仍存在的漏洞与建议

### 2.1 点击窗口关闭（X）未触发系统停止

- **现象**：用户点标定窗口的 X 时，只执行了 Tk 的 destroy/close，**没有**调用 `request_system_stop()`。
- **后果**：mainloop 退出后，主线程会卡在 `while not stop_event.is_set(): ...` 等待识别线程，退出不干净（需等超时或 Ctrl+C）。
- **建议**：在 `EyeCalibrationApp` 初始化后绑定 `self.root.protocol("WM_DELETE_WINDOW", handler)`，在 handler 里调用 `request_system_stop()`（需从 `project.main` 引入），再执行原有关闭逻辑。

### 2.2 标定点提交时在主线程做拟合，会卡 UI

- **现象**：用户每确认一个标定点，UI 发出 `CALIBRATION_POINT_SUBMIT`；`FittingScheduler._on_calibration_point_submit` 在**主线程**执行（因为 emit 来自主线程），其中同步调用 `fit_all_eyes(data)`。
- **后果**：每次提交都会短暂阻塞主线程，标定过程中可能感到界面卡顿。
- **建议**：将「根据 calibration_response 算 eyeball/pupil 并写入 SAMPLES_STORAGE」放进拟合池或单独后台任务，回调里只做轻量校验与提交任务，结果再写存储；或至少用 `thread_pool.submit(...)` 包一层，避免在主线程跑 `fit_all_eyes`。

### 2.3 主流程仍直接依赖 EyeCalibrationApp 单例

- **现象**：`main()` 里用 `EyeCalibrationApp.get_instance()` 做 `check_system_status` 的调度（`ui.root.after(100, check_system_status)`）以及 finally 里 `calibration_ui.close()`。
- **后果**：若将来改为「无 Tk、仅 Unity 或 Web 前端」时，主流程没有可用的「前端」引用，需要改 main 的编排方式（例如用事件或注册的 FrontendAdapter 获取「是否有前端、是否需轮询」）。
- **建议**：短期可保留现状；若计划支持无 Tk 启动，可引入「当前前端适配器」注册表或事件（例如「前端已就绪 / 已关闭」），main 只依赖适配器接口或事件，不依赖 `EyeCalibrationApp` 类名。

### 2.4 事件契约仍分散

- **现象**：事件名、payload、谁发谁收分布在 `event_types.py`、`main.py`、`ui.py`、`FittingManager` 等处。
- **建议**：在 `docs/` 或 `events/` 维护一份「事件接口表」（例如在《前后端与接口分析》中补充 `GAZE_POINT_UPDATE`、`REQUEST_CALIBRATION_UI_CLOSE` 及方向与 payload），便于后续接 Unity/Web 时对照。

---

## 三、小结

| 维度 | 结论 |
|------|------|
| **是否更简明合理** | 是。事件驱动 + 线程分离 + FrontendAdapter 抽象，前后端连接方式更清晰，扩展性更好。 |
| **是否还有漏洞** | 有。主要是：窗口关闭未发系统停止、标定点提交在主线程做拟合导致卡顿、main 仍紧耦合 Tk 单例、事件契约未集中文档化。建议优先修「窗口关闭 → request_system_stop」和「标定点提交 → 拟合入池」，其余按需逐步收口。 |
